---
name: run
description: Use when a person states a goal for this project, when a plan file exists that should be executed, or when a run is stopped at a decision. Drives chongdae's run loop: relays each stop to the person, writes the artifacts the session is asked for, and never advances past a gate on its own.
---

The engine is `chongdae.py` at this plugin's root — the session-start line `chongdae: …` gives its full path; there is no `chongdae` binary: `python3 "<that path>" <command> --target <project>` (`python` on hosts that have no `python3`). The order of steps lives in the engine.

0. `status` first: it says whether a run is in progress and never fails. To know what happened in a run — before a retrospective, or to pick up where a run stopped — `show` (`--run ID`, `--since REV` for a line per run, `--path FILE` for the tasks that touched a file), not the record's JSON. Writes to the project need a run in progress (the PreToolUse hook refuses them otherwise).
   Before a run: when the goal is a complaint about something that exists ("I don't like X"), ask what is wrong with it before choosing how to change it — building the wrong remedy costs a run. List everything the work needs from the person (files and their formats, each one's rules, the decisions) and ask for it in one go: a run started on half the materials becomes several runs.
   Weigh the procedure against the change: for a change of a few lines whose check you can name, hiring a test writer, a builder and a verifier costs more than the change — ask the person, and on their word take it yourself: `add <id> --role session --why "<the size of it, and their word>" --by <name> --check ...` (recorded as `self-performed`, its reason counted). Keep the hired path for work whose contract someone else should read.
   Before sending a build out: whatever it needs from outside the tree — packages, a lock file, a tool — is installed by you, in the session, first: a worker's sandbox may have no network and a read-only `.git`, and a worker told to install what it cannot reach improvises (a hand-written lock file, the old tool in a new wrapper). `--tests` takes one path per argument (`--tests tests/a.py tests/b.py`, never one quoted `$(ls …)` string). `--tests` on a task with a `--check` protects those files — its judgment restores any change to them (`add` prints which meaning applies). When a build's contract tests are wrong (a test error, something this machine cannot run), never fix them inside the build or in a task that names them with `--tests` and a check: `dispute <build> --tests FILE --why "…"` reopens the task that wrote them (or makes one), you amend them there, and the build keeps the fix. A task's `--check` is what must pass for this task: a check the brief says may still fail belongs to a later task, not this one.
   When a build or its tests need what a worker's sandbox may not give — a local port (a dev server, a fake S3, `wrangler dev`), the network — say so: `add ... --requires loopback` (or `network`); a member that cannot give it refuses at once instead of failing after a build; a lock role `implementer@loopback` (the same member on a host whose sandbox can) is then hired for it. A member whose sandbox lacked a capability (mid-task, or a refusal before starting) goes to the lock's alternate that can, with no stop. With no alternate, chongdae takes the task for the session itself (the project decided this once, at setup: hunsu.json `capabilities`) and `run` stops with `decision: session agent: <id>: … taken by the session: <reason>` — do its work and `run` again, as for any task you took; do not stop to ask the person, and do not `take` it again. The run is meant to go on without a person; `report` counts these tasks for the reviewer. Add a task before you write its work: two open session tasks share one tree and each measures from its own `add`, so a file written for the second before it was added, or while both were open, can be counted by whichever finishes first. When `run` or `retry` says so (`note: FILE ... chongdae adopt ...`), or a verifier finds the work beside an empty `touched`, `adopt <task> FILE... --why "…"` is the judgment that gives the file to its task — never drop the task and add it again (the new one records nothing). When a hired task stopped but its work is in the tree and you finish it (the sandbox could not run its tests; a guard read your own concurrent edits), `take <id> --why "..."` — never `drop`: a drop records done work as not done. When you ran the check that shows the work holds (the full test run a worker could not show), give it as `--checked "<command>"` (on `take` or `retry`): chongdae runs it itself and hands the result to the verifier — a command you ran and only describe reaches nobody. A tests task's red run (the new tests failing before the build) is `--checked-red "<command>"`: a non-zero exit is recorded as red as expected, a zero exit as passed before the build. When a tests task deletes test files the contract retires, leave them in the build's `--tests` if they were there: `add`/`run` say "deleted by the contract", the build is sent them as `deleted-tests`, and a build that recreates one is refused — never drop and re-add the build to get rid of them.
   When you dispatch work to your own sub-agents (the host's Agent tool) — because the person asked, or the lock names `subagent` for a role — add each piece as `add <id> --role subagent --scope <the files/dirs that sub-agent may touch> ...` BEFORE dispatching it: the task is the sub-agent's (declared hands, `performed_by.provider: subagent`), not yours, and not `self-performed`. Give concurrent sub-agents disjoint scopes, the same ones you tell them in their prompts: a changed file is then the open task's whose scope holds it most narrowly, whichever finishes first; `run` says a file in two scopes or in none (`note: scope: …`) with the `adopt` that settles it. Never record a sub-agent's work as your own task.
   Sign only what a person decided: `--by NAME` is the person's word, given for this judgment. A drop, take, retry, claim, adopt or `--role session --why` you decide yourself takes no `--by` — the record signs it as the session (your host and model), and `show`/`report` say so. Never write the owner's name on your own judgment, and never `--delegated` one the person did not hand off; the gates (`confirm`, `accept`) still need the person's `--by` or their delegation.
   An operation outside the repository — a deploy, deleting a secret, a bucket or a database, a remote database change, a DNS or access change — goes through `did <task> --why "…" -- <command> <args>` (one command, no shell line), or several that are one decision as `did <task> --why "…" --each <file>` (one command per line, one commit; a failure stops the rest), never as plain Bash: chongdae runs it, records the command, its exit and its output's end on the task whatever the exit, and `report` shows it to the reviewer. When it cannot be undone, cite where the person agreed: `--approved-in source:<id>` (keep their words first with mangsang `source`); if they have not agreed, ask before running it. Prose in a plan file is not a record of what ran.
   The PreToolUse hook adds a line of context when a Bash command reads as such an operation (`git push`, `npm run deploy`, `wrangler deploy`, …) while a run is in progress: that is the cue to run it as `did` instead. An operation goes before `close`, never after it on the same line (`close; git push` pushes outside any run, where nothing records it). `close` stops on a done task whose brief reads as an operation (deploy, push, publish, delete, 배포, 푸시, 삭제 …) with no `did`.
   A session task with no check that leaves nothing in the tree (a decision, an answer) is done only when you name it: `run <task>`. Unnamed, a task with no change of its own and no `did` stays open — `run` says so (exit 2) and goes on with the others: never let a `run` for one task stand for another whose work has not happened yet. When `add` or `run` offers `chongdae add TASK --check "…"` (the check the project declares for those paths, hunsu.json `settings.chongdae.checks-for`), run that line: the check then decides the task. A task whose work is another product's records (`hunsu lock`, a mangsang confirm) names them in its `--scope` (`--scope hunsu.json hunsu.lock.json`, `--scope mangsang`): inside its own scope they count as its work, and `run` prints their commit lines.
   Commit a task's work with the subject `run-<id>/<task> (session): <what>` — `run` and `close` print the exact `git add -- …` and `git commit -m "…" -- …` lines; `run-<id>: …` (no task) is chongdae's own record commits, never yours.
   Every command that changes the record (`confirm`, `accept`, `retry`, `take`, `drop`, `dispute`, `adopt`, `did`, `close` — and any other tool's that writes a record) runs on its own and its exit code is read — never chained with `;`, never piped through `tail`: a failure hidden there is a run closed on a step that did not happen.
1. A new goal: `init --goal "<the person's sentence>"` (the bootstrap plan). A piece of work with no plan: `init --session --goal "..."` (add `--from plan/PLAN.md` when a plan document exists, so tasks can `--closes Q-…` and the people you hire get those sections — without it a quibbler or verifier would get an empty contract, so `add` warns and `run` refuses to send them one), then `add <id> --brief "..."` per piece, `run` to record it, `close` at the end. A plan you wrote: `init --plan -` with the JSON on stdin (a heredoc; the write gate refuses a plan file in the tree before its run exists, and the run keeps the copy that matters) or `init --plan <file>` (it must have `artifact-type: chongdae/plan@1`, tasks with `role`, and either `path` or `checks` — otherwise it is refused). In a session run the lock says who does a task: `add <id> --check …` goes to the lock's `implementer` (a fresh process builds it from the brief and checks), `add <id> --tests F` where F does not exist yet goes to its `nitpick` (it writes the contract's tests), a task with neither (a plan section, a model) is yours. Do not take a build or a test task yourself because it looks small: if you must, say why — `--role session --why "…"` — it is recorded on the task and reported. `add … --before quibble` has the contract quarrelled with first; `--after newbie` has the result tried by someone who knows nothing, before the gate.
   On a project with git history, prefer `--worktree`: the run gets its own worktree and branch (the init output names the path — every later command needs `--target <that path>`, and edits go there, not in the shared tree). `close` commits the worktree and merges it back (a session run: when you close it; a plan or bootstrap run: after `run` completed it) — a conflict or a red recheck comes back as a `decision:` line telling you to resolve in main and `init --merge`. Inside the worktree the write gate is that worktree's: its own run must be open.
   Many machines (or several sessions) on one plan: when hunsu.json declares `settings.chongdae.lease`, a claim is a hold, not a record line. `claim <id>` before working a task (one at a time; lost → it names who holds it and the ready unheld tasks — take one of those, never the held one); `claim --list` shows every hold with its age and last progress. `run` advances only the tasks you hold and takes the next ready unheld one itself; your hold is renewed by your progress, not by time — a task you leave waiting for hours lapses and someone else may take it. When `run` says `this session's hold (gen N) was taken — … holds it now`, stop working that task (your result under gen N will be refused); leave the work in the tree or branch and tell the person. Never `claim --break` a live hold on your own: it takes over someone's work — only on the person's word, with `--why "<their reason>"` (and `--by <name>`). For one task of a plan done on its own branch, `init --session --worktree --parent <run>/<task>` (the parent's `show` lists its children). When the project declares `settings.chongdae.remote` (`sync` or `shared`), chongdae pushes its own record commits — do not push the record yourself; under `shared` a `decision:` that the remote did not take a push means: fetch, reconcile, push, then go on.
2. `run`. Exit 2: the last line (`decision: ...`) says who must act. Exit 4: `still working: …` — a call takes at most about four minutes (one budget for the whole call: chongdae's own checks, the verifier and every provider it starts), then hands back; call `run` again, as many times as it takes; each call resumes the same work where it stopped (`<task>.pending.json`, `<task>.checks.pending.json`). Read the exit code of `run` itself — not of a pipe around it. Never background `run` and never end the session while a provider is out: the provider is this session's child and dies with it, and there is no notification to wait for.
   - `<task>: quibble found N thing(s) the contract leaves open` — a `before` role's findings, each with a quote. Decide each in the plan (write the answer into the section, or say why it stays open), then `accept <task> --by NAME | --delegated WHY` and `run` again; the work does not start before that.
   - `session agent: produce ...` — you write that artifact at that path (questions, plan document, or code that makes the checks pass), then `run` again.
   - `session agent: dispatch <task> to this host's own subagent ...` — a `native:` provider. Run the argv it names (`... --prompt-only`) to get the prompt; start a FRESH subagent of this host with that prompt as its whole task (Claude Code: the Agent tool, general-purpose, run in the foreground; Codex: spawn_agent and wait); write the subagent's final JSON answer verbatim to the response path it names (a heredoc is fine — the path is in the run's record dir); then `run` again. Never do the subagent's work yourself and never edit its answer: the record says the session relayed it, and a relay that edits is a lie.
   - `human: review ...` — show the person the artifact or the passing checks; on their word `confirm <task> --by <name>`; if they delegated the call, `confirm <task> --delegated "<why>"` — the reason is recorded. If the person pre-approved a whole batch of judgments ("everything in this run is delegated"), declare it ONCE PER RUN: `delegate --scope confirm,accept,retry --why "<their words>" --by <name>` prints an id `D-xxxx` (a delegation belongs to the run it was declared in — the run is the unit of judgment — so a new run gets its own); every later judgment in that run then references it as `--delegated D-xxxx` (recorded as a ref to that one judgment). Do not paste the same reason string into judgment after judgment — `report` flags a reason repeated 3+ times as `delegation-stamp`: one judgment claiming to be many.
   - `the provider made N decision(s)` — show them; the person writes the accepted ones into the plan, then `accept <task> --by|--delegated`.
   - `role ... has no provider` — the person declares one in `hunsu.json` `roles` or the plan's `providers`; do not stand in for a role.
3. `close` stops for you (exit 2, `decision: session agent: …`) when a finished task's work is not committed — commit it (`git add -- FILE…`, `git commit`) and close again — or when the reviewer, which runs before the close is final, found objections the tree can answer (cq-failed, stale relations, a contradiction): fix each and close again. Not a person's question; `close --anyway --why "…"` only when the person said to close with them standing. Exit 0 with `complete` (or `close` of a session run): report the run's non-claims to the person. The lock's `reviewer` role ran as the run ended (its line is in the output; what it wrote went into the close commit) — you do not run a review yourself; what its findings need from a person, the reviewer says at the next session start. The engine has been notarizing the record all along — every judgment (init, confirm, accept, retry, drop, close, complete, landing) commits `.chongdae/run-<id>/` and only it, so the record needs no commit from you; commit the *work* (code, tests, documents) as usual, before `close`. If the engine could not commit (no git identity, say), it says nothing and the record simply sits uncommitted — then commit it with the work.
4. After a merge: `recheck`; anything red is not done on this tree. Its output and exit code are the verdict (a merge run's task carries it); it files nothing.

Never edit `.chongdae/` by hand except to reset a task whose result was lost; record why in the run's non-claims.
